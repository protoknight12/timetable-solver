## 6.1. Изисквания

| Какво | Изискване |
|---|---|
| Операционна система | Linux (`install.sh` е писан с мисъл за Ubuntu/Debian). Windows и macOS са само за разработка (вижте [2.2](02-quick-start.md#22-пускане-на-windows-или-macos-за-разработка)). |
| Софтуер | Docker Engine и Docker Compose v2 (командата `docker compose`). Скриптът **не** ги инсталира. Нужни са и `git` (за изтегляне на кода) и `bash`. |
| Процесор | Решаващият алгоритъм използва до 8 ядра (колкото са достъпни). Повече ядра означават по-бързо търсене при голямо училище. Не са измервани минимални изисквания за памет. |
| Мрежа | Порт 8000 (или 443 при HTTPS прокси). Сървърът има нужда от интернет при инсталиране (изтегляне на образи и пакети) и за ИИ. **Браузърите** на потребителите имат нужда от интернет, защото Bootstrap, иконите и HTMX се зареждат от jsDelivr CDN. |
| Браузър | Съвременен Chrome, Edge, Firefox или Safari. |

## 6.2. От какво се състои

`docker compose` пуска четири услуги:

| Услуга | Образ | Роля |
|---|---|---|
| `web` | изгражда се от `Dockerfile` (Python 3.12, Gunicorn) | Уеб приложението на порт 8000 |
| `worker` | същият образ, команда `rq worker` | Изгражда разписанията във фонов режим |
| `db` | `postgres:16` | Базата данни. Данните са в Docker том `db-data` |
| `redis` | `redis:7` | Опашката за изчисленията и броячите за ограниченията на заявките |

Всички услуги се рестартират автоматично (`restart: unless-stopped`), включително след рестарт на сървъра,
ако Docker се стартира при зареждане.

## 6.3. Инсталиране с install.sh

```bash
git clone https://github.com/protoknight12/timetable-solver.git saturn
cd saturn
./install.sh
```

Какво прави скриптът, стъпка по стъпка:

1. Проверява, че има Docker и Docker Compose v2 и че Docker отговаря. Ако потребителят не е в групата `docker`,
   пуснете скрипта със `sudo`.
2. Ако няма файл `.env`, го създава от `.env.example` (с права само за собственика) и:
    - генерира случаен `SECRET_KEY` и случайна парола за базата (`POSTGRES_PASSWORD`);
    - пита за ключ за Anthropic API (не се показва при писане). Празно = без ИИ (`LLM_ENABLED=false`).
3. Изгражда и пуска услугите (`docker compose up -d --build`).
4. Създава или обновява таблиците в базата (`flask db upgrade`).
5. Ако още няма администратор, пита за потребителско име (без интервали, до 64 знака) и парола (поне 8 знака,
   два пъти). Паролата не се появява в историята на командите.
6. Показва адреса: `http://<IP на сървъра>:8000`.

Скриптът **може да се пуска отново**: съществуващите `.env`, база и администратор не се променят. Затова се използва
и за обновяване (вижте [6.10](#610-обновяване)).

> **Не изтривайте `.env`, докато съществува томът `db-data`.** Новата генерирана парола няма да съвпада със старата
> база и приложението няма да може да се свърже с нея.

След инсталирането:

- Ако искате данни за проба: `docker compose run --rm web flask --app app seed seeds/demo_school.json`.
- Сложете HTTPS (следващата точка). **Без HTTPS входът работи само от самия сървър** (`http://localhost:8000`).

## 6.4. HTTPS и обратен прокси

**Защо е задължително.** Извън режима за разработка бисквитката за вход се изпраща само по защитена връзка
(`Secure`). Браузърите приемат такава бисквитка по обикновен HTTP само от `localhost`. Затова от друг компютър адрес
като `http://192.168.1.20:8000` показва страницата, но **входът не се запазва** (връща ви на страницата за вход или
дава грешка „Невалидна заявка“). Нужен е обратен прокси с HTTPS пред приложението.

`docker-compose.yml` вече казва на приложението, че пред него има **един** прокси (`TRUSTED_PROXIES: "1"`), за да
вижда истинския адрес на потребителя и протокола.

**Пример с [Caddy](https://caddyserver.com/)** (инсталиран на същия сървър). Файл `/etc/caddy/Caddyfile`:

С публичен домейн (Caddy сам взима сертификат от Let's Encrypt):

```
saturn.example.bg {
    reverse_proxy 127.0.0.1:8000
}
```

В училищна мрежа без домейн (Caddy използва свой вътрешен сертификат; браузърите ще покажат предупреждение,
освен ако основният сертификат на Caddy не е инсталиран на компютрите):

```
https://192.168.1.20 {
    tls internal
    reverse_proxy 127.0.0.1:8000
}
```

После `sudo systemctl reload caddy`. Може да се използва и друг прокси (nginx, Apache), стига да подава
`X-Forwarded-For`, `X-Forwarded-Proto` и `X-Forwarded-Host`.

**Затворете директния достъп до порт 8000.** Щом приложението вярва на един прокси, някой, който се свързва
директно на порт 8000, може да подправи заглавката `X-Forwarded-For` и така да заобиколи ограниченията на опитите
за вход. Затова порт 8000 трябва да е достъпен само от самия сървър:

- на VPS: защитна стена на доставчика, която пропуска само портове 22, 80 и 443; или
- файл `docker-compose.override.yml` до `docker-compose.yml` (нужен е Docker Compose 2.24.4 или по-нов),
  последван от `docker compose up -d`:

```yaml
services:
  web:
    ports: !override
      - "127.0.0.1:8000:8000"
```

> Обикновената защитна стена `ufw` **не** спира портовете, които Docker публикува, затова не разчитайте само на нея.

Ако нямате прокси и не искате такъв (например само за проба на един компютър), задайте `TRUSTED_PROXIES` на `0`
в `docker-compose.override.yml` и използвайте само `http://localhost:8000`.

## 6.5. Настройки (.env)

Файлът `.env` е в папката на проекта. Никога не го качвайте в Git. След промяна изпълнете `docker compose up -d`,
за да се приложи.

| Настройка | По подразбиране | Значение |
|---|---|---|
| `SECRET_KEY` | (генерира се) | Таен ключ за бисквитките и CSRF. Без него всеки рестарт излиза от профилите и няколко процеса на Gunicorn не работят заедно. |
| `POSTGRES_PASSWORD` | (генерира се) | Паролата на базата в Docker Compose. Сменя се само преди първото пускане. |
| `DATABASE_URL` | — | Адрес на базата. В Docker Compose се задава автоматично. Без него (извън Docker) се използва временна база в паметта. |
| `REDIS_URL` | `redis://localhost:6379/0` | Адрес на Redis. В Docker Compose се задава автоматично. |
| `ANTHROPIC_API_KEY` | празно | Ключ за ИИ. |
| `LLM_ENABLED` | `false` | `true` включва полето за правила с думи. |
| `LLM_MODEL` | празно = `claude-sonnet-5-5` | Моделът на Anthropic. |
| `SOLVER_TIME_LIMIT_S` | `60` | Най-много секунди за едно изчисление. Винаги се пази най-доброто намерено разписание. |
| `SOLVE_INLINE` | `false` | `true` = изчисление в уеб процеса без Redis и работен процес. **Само за разработка.** |
| `TRUSTED_PROXIES` | `0` (в Compose: `1`) | Колко прокси сървъра пред приложението да се смятат за доверени. Никога над 0 без прокси. |
| `DEMO_ADMIN_PASSWORD`, `DEMO_VIEWER_PASSWORD` | празно | Ако са зададени, `flask seed` създава профилите `admin` (Администратор) и `preglad` (Преглед) с тези пароли. Иначе ги пропуска. |
| `API_TOKEN` | празно | Ключ за REST API за други системи (вижте [7](07-api.md)). Празно = API само за влезли потребители. Генериране: `python3 -c "import secrets; print(secrets.token_urlsafe(32))"` |

Стойности, които са фиксирани в кода (не се настройват):

| Какво | Стойност |
|---|---|
| Учебни дни | 5 (понеделник–петък) |
| Опити за вход и регистрация | 5 в минута |
| Пускане на изчисление | 5 в минута на администратор |
| Заявки към ИИ | 5 в минута на администратор и 100 на ден за цялото училище; до 1000 знака |
| Публична страница на клас | 60 в минута от един адрес |
| REST API | 120 в минута на потребител или адрес |
| Качване на файл | до 2 MB (шаблон), до 32 MB (експорт от aSc) |
| Минимална дължина на парола | 8 знака |

## 6.6. Включване на изкуствения интелект

1. Вземете ключ от [Anthropic Console](https://console.anthropic.com/).
2. **Задайте месечен лимит на разходите** на ключа в конзолата. Това е последната защита срещу неочаквани разходи.
3. Добавете в `.env` двата реда по-долу.
4. Изпълнете `docker compose up -d`.

```ini
ANTHROPIC_API_KEY=sk-ant-...
LLM_ENABLED=true
```

Без ключ или с `LLM_ENABLED=false` полето за правила с думи е скрито и всичко останало работи нормално.

## 6.7. Профили: смяна на парола и изтриване

Нов профил:

```bash
docker compose run --rm web flask --app app create-user ivan.petrov --role viewer
```

Паролата се пита два пъти. Ролята е `admin` (Администратор) или `viewer` (Преглед). Ролята се сменя и от менюто
„Потребители“.

**Смяна на забравена парола** (засега няма бутон в интерфейса):

```bash
docker compose run --rm web flask --app app shell
```

и в отворената конзола:

```python
from werkzeug.security import generate_password_hash
from app.models import User, db
u = db.session.scalar(db.select(User).filter_by(username="ivan.petrov"))
u.password_hash = generate_password_hash("нова-парола-поне-8-знака")
db.session.commit()
```

**Изтриване на профил:** в същата конзола намерете потребителя както по-горе и изпълнете
`db.session.delete(u)` и `db.session.commit()`. Изходът от конзолата е `exit()`.

## 6.8. Ежедневна работа: старт, стоп, логове

| Действие | Команда |
|---|---|
| Състояние на услугите | `docker compose ps` |
| Спиране | `docker compose stop` |
| Пускане | `docker compose start` |
| Рестарт след промяна в `.env` | `docker compose up -d` |
| Логове на живо | `docker compose logs -f web worker` |
| Последните 200 реда | `docker compose logs --tail 200 worker` |
| Спиране и премахване на контейнерите (данните остават) | `docker compose down` |

> **Внимание:** `docker compose down -v` изтрива и тома с базата, тоест **всички данни**.

## 6.9. Архивиране и възстановяване

Засега няма скрипт. Архивирането се прави ръчно.

**Архивиране** (може да се пуска всеки ден, например от `cron`):

```bash
docker compose exec -T db pg_dump -U saturn saturn > saturn-$(date +%F).sql
```

Пазете и копие на `.env` на сигурно място: в него са `SECRET_KEY` и паролата на базата.

**Възстановяване** в същата инсталация:

```bash
docker compose stop web worker
docker compose exec -T db dropdb -U saturn saturn
docker compose exec -T db createdb -U saturn saturn
docker compose exec -T db psql -U saturn -d saturn < saturn-2026-11-26.sql
docker compose start web worker
```

**Леко копие на данните от интерфейса:** „Данни → Импорт от Excel → Изтегли текущите данни“ дава Excel файл с
учителите, предметите, стаите, класовете, групите, учебните часове и учебния план. Той **не** съдържа
ограниченията, разписанията, профилите и нормите на учителите.

## 6.10. Обновяване

1. Направете архив (вижте [6.9](#69-архивиране-и-възстановяване)).
2. Изтеглете новия код и пуснете отново инсталатора. Той изгражда образа, прилага новите промени в базата и
   не пипа `.env`, данните и профилите:

```bash
git pull
./install.sh
```

Ръчно същото е `docker compose up -d --build` и после `docker compose run --rm web flask --app app db upgrade`.

## 6.11. Какви данни напускат сървъра

- **Към Anthropic** (само ако ИИ е включен и администраторът натисне „Предложи“): текстът на заявката и списъците с
  имена на учители, класове, предмети, стаи, учебни планове и часовете на звънеца. Нищо друго.
- **Към jsDelivr CDN:** браузърите изтеглят Bootstrap, иконите и HTMX. Данни на училището не се изпращат.
- Нищо друго не се изпраща навън. Всички данни са в базата на училищния сървър.

## 6.12. Отстраняване на проблеми

| Проблем | Причина и решение |
|---|---|
| След вход ме връща на страницата за вход или пише „Невалидна заявка“ | Влизате по HTTP от друг компютър. Нужен е HTTPS (вижте [6.4](#64-https-и-обратен-прокси)) или `http://localhost:8000` на самия сървър. |
| Страницата е без стил (обикновен текст, без цветове) | Браузърът няма интернет и не може да изтегли Bootstrap от CDN. |
| Изчислението стои „На опашка“ | Работният процес не върви. Проверете `docker compose ps` и `docker compose logs worker`. Изчисление, което стои много по-дълго от лимита, се отбелязва като неуспешно при следващия опит за изграждане. |
| „Изчислението не може да бъде стартирано“ | Redis не отговаря. Проверете `docker compose ps redis`. |
| „Не е намерено решение в зададеното време“ | Увеличете `SOLVER_TIME_LIMIT_S` (например на 120) или дайте повече процесорни ядра на сървъра. |
| „Липсва ключ за изкуствения интелект.“ | `LLM_ENABLED=true`, но `ANTHROPIC_API_KEY` е празен. |
| „Услугата не отговори. Опитайте отново след малко.“ | Няма връзка с Anthropic, ключът е невалиден или е изчерпан лимитът на разходите. Вижте `docker compose logs web`. |
| „Твърде много опити“ (грешка 429) | Достигнато е ограничение на заявките (вижте таблицата в [6.5](#65-настройки-env)). Изчакайте. |
| „Файлът е твърде голям“ (грешка 413) | Файлът е над 2 MB (шаблон) или 32 MB (aSc). |
| „PDF изтеглянето не е налично на този сървър“ | Липсват системните библиотеки на WeasyPrint. В Docker образа те са инсталирани; проблемът е само при ръчна инсталация (нужни са pango, harfbuzz и шрифт с кирилица). Използвайте „Печат“. |
| Приложението не се свързва с базата след преинсталиране | Изтрит е `.env`, а томът `db-data` е стар. Върнете стария `.env` от архива. |

Повече отговори има в [10. Чести въпроси, проблеми и ограничения](10-faq.md).
