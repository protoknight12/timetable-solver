## 8.1. Архитектура

```
              ┌─────────────────────┐
 Браузър ────►│ web (Flask+Gunicorn)│────► PostgreSQL 16 (данни, правила като JSONB, разписания)
 (Jinja2,     └──────────┬──────────┘
  HTMX,                  │ задача „изгради“
  Bootstrap)             ▼
                    ┌─────────┐      ┌──────────────────────────────────────────┐
                    │  Redis  │◄────►│ worker (RQ)                              │
                    └─────────┘      │  база → обикновени данни (SolverInput)   │
                                     │  solver/  (CP-SAT)                       │
                                     │  checker/ (чист Python)                  │
                                     │  запис на уроците и нарушенията          │
                                     └──────────────────────────────────────────┘

 web ────► Anthropic API (само текст → предложени правила)
```

Четири услуги в Docker Compose: `web`, `worker`, `db`, `redis` (вижте [6.2](06-installation.md#62-от-какво-се-състои)).

**Защо е разделено така (категория „Разпределени приложения“):**

- **Изчислението е в отделен процес** (`worker`), а не в уеб заявката. Голямо училище може да отнеме до 60 секунди;
  страницата остава отзивчива и проверява състоянието на всеки 2 секунди с HTMX.
- **Решаващият алгоритъм и проверката са чисти Python пакети** без Flask и база данни. Те получават обикновени
  данни и връщат обикновени данни. Могат да се тестват отделно, да се преместят на друга машина или да се
  използват от друго приложение.
- **Един скрипт** (`install.sh`) пуска целия стек на всеки Linux сървър с Docker.

**Граници между пакетите** (проверяват се при преглед на кода):

| Пакет | Може да внася | Не може да внася |
|---|---|---|
| `app/` | всичко | — |
| `schema/` | стандартната библиотека, Pydantic | Flask, SQLAlchemy, `app/` |
| `solver/` | `schema.contract`, OR-Tools | Flask, SQLAlchemy, `app/` |
| `checker/` | стандартната библиотека, `schema/` | Flask, SQLAlchemy, `app/`, **`solver/`** |

Проверката нарочно не внася и не копира код от алгоритъма. Така една грешка в алгоритъма не може да се повтори и в
проверката.

## 8.3. Какво става при „Изгради разписание“

1. **Уеб процесът** (`app/routes/solve.py`, `start`): проверява ролята и ограничението 5 в минута; отбелязва като
   неуспешни „заседнали“ изчисления; отказва, ако друго изчисление още върви. Създава ред `SolveJob` със състояние
   `queued` и го слага в опашката на RQ (с време за изпълнение = лимита + 60 секунди).
2. **Работният процес** (`app/jobs.py`, `run_solve`): отбелязва `running` и чете базата.
3. `build_solver_input` (`app/solver_input.py`) превръща редовете от базата в `SolverInput`: обикновени неизменими
   обекти, подредени по `id`. Взима **само потвърдените** ограничения. Тук се прилагат и правилата за стаите:
   предмет с компютри или с избрани стаи винаги изисква стая; позволените стаи на частта имат предимство пред тези
   на предмета; типът стая по подразбиране на предмета се попълва.
4. `SolverInput.problems()` проверява данните (изтрити записи, празнини в часовете, част без подходяща стая и др.).
   При проблем изчислението спира с обяснение на български и **не** се решава с грешни данни.
5. `solver.solve(...)` подрежда часовете (вижте [8.6](#86-решаващият-алгоритъм)). Ако е избрано „Запази колкото може
   повече…“, получава и уроците на предишната версия като `reference`.
6. `checker.check(...)` проверява резултата независимо (вижте [8.7](#87-независимата-проверка)).
7. Уроците (`Lesson`), нарушенията (`Violation`) и, при невъзможност, номерата на конфликтните ограничения се
   записват в базата. Състоянието става `finished`.
8. **Браузърът** пита за състоянието на всеки 2 секунди (`/jobs/<id>/card`). Когато изчислението свърши,
   страницата се презарежда и показва резултата.

Всяка неочаквана грешка се записва в лога, а изчислението става `failed` с общо съобщение. То никога не остава
„изчислява се“ завинаги.

## 8.4. Модел на данните

Моделите са в `app/models.py`. Основната идея: **учебният план** (`Course`) е една единица от разписанието с часове
седмично, разделени на блокове. Алгоритъмът дава на всеки блок ден и начален час. **Частта** (`CoursePart`) казва
какво правят определени групи през това време. Всички части на един учебен план са едновременно, затова един
модел покрива обикновени часове, съвместни часове на няколко класа, паралелни групи и „едната група няма час“.

| Таблица | Основни полета |
|---|---|
| `teachers` | `name`, `short_name`, `weekly_norm` (норма, само за справката) |
| `subjects` | `name`, `short_name`, `default_room_type`, `color`, `requires_computers` |
| `subject_rooms` | връзка предмет ↔ стая (стаите, в които се води предметът) |
| `rooms` | `name`, `type` (код: `classroom`, `lab`, `lecture`, `gym`, `workshop`, `other`), `concurrent_capacity`, `has_computers`, `seats` |
| `school_classes` | `name` (8А), `grade`, `student_count`, `class_teacher_id`, `public_token` |
| `student_groups` | `class_id`, `name`, `is_whole`, `split`, `student_count`. Точно една група `is_whole` на клас (уникален индекс). |
| `periods` | `number` (първичен ключ), `start_time`, `end_time` |
| `courses` | `periods_per_week`, `block_sizes` (JSON, например `[2, 1]`), `label`, `week` (`null`, `"A"`, `"B"`) |
| `course_parts` | `course_id`, `subject_id`, `needs_room`, `room_type`, `allowed_room_ids` (JSON) |
| `course_part_groups`, `course_part_teachers` | връзки част ↔ групи и част ↔ учители |
| `constraints` | `type`, `params` (JSONB), `hard`, `weight`, `status` (`proposed`/`confirmed`/`rejected`), `source` (`manual`/`llm`/`import`), `original_text`, `created_at` |
| `solve_jobs` | `status` (`queued`/`running`/`finished`/`failed`), `solver_status`, `objective`, `error`, `time_limit_s`, `base_job_id`, `published_at`, `created_by_id`, времена |
| `lessons` | `job_id`, `course_id`, `part_id`, `day`, `start_period`, `length`, `room_id`. Един ред за всяка част и всеки блок. |
| `violations` | `job_id`, `type`, `entity_ids` (JSON), `message_key`, `hard`, `constraint_id`. Конфликтните ограничения се пазят тук с тип `infeasible_core`. |
| `users` | `username`, `password_hash`, `role` (`admin`/`viewer`), `teacher_id` (уникален) |

**Изтриване:** учител, който преподава, не може да се изтрие (RESTRICT). Изтриването на учебен план изтрива и
частите и уроците му (CASCADE). Изтриването на стая оставя старите уроци без стая (SET NULL). Уроците и
нарушенията принадлежат на своето изчисление (CASCADE). Профилите не се изтриват при `flask seed --reset` и при импорт.

**Препратки в JSON.** Параметрите на ограниченията съдържат номера (например `teacher_id`) в JSON, затова базата не
може да ги провери. Тази проверка прави `SolverInput.problems()` преди всяко изграждане и при всяко въвеждане на
ограничение.

Промяна в схемата на базата става само с миграция и след съгласие на двамата разработчици.

## 8.5. Договорът между приложението, алгоритъма и проверката

Файлът [`schema/contract.py`](../schema/contract.py) описва точно какво получава алгоритъмът (`SolverInput`) и какво
връща (`SolveResult`). Той е на чист Python (само стандартната библиотека). Текуща версия: **4**
(2: разделяния на групи; 3: седмици A/B; 4: компютри и места). Данни с версия 2 още се приемат.

Пълни примери: [`schema/examples/split_practice.json`](../schema/examples/split_practice.json) и
[`schema/examples/ab_weeks.json`](../schema/examples/ab_weeks.json).

```json
{
  "contract_version": 4,
  "days": [1, 2, 3, 4, 5],
  "periods": [1, 2, 3, 4, 5, 6, 7],
  "teachers": [{"id": 7}, {"id": 8}],
  "subjects": [{"id": 4}, {"id": 5}],
  "classes": [{"id": 1, "name": "9А", "grade": 9}],
  "groups": [
    {"id": 1, "class_id": 1, "is_whole": true},
    {"id": 2, "class_id": 1, "is_whole": false, "name": "Група 1", "split": "групи"},
    {"id": 3, "class_id": 1, "is_whole": false, "name": "Група 2", "split": "групи"}
  ],
  "rooms": [{"id": 1, "type": "lab", "concurrent_capacity": 1}],
  "courses": [{"id": 1, "periods_per_week": 2, "block_sizes": [2], "parts": ["..."]}],
  "constraints": [{"id": 1, "type": "fixed_slot", "hard": true,
                   "params": {"course_id": 1, "blocks": [{"day": 5, "start_period": 1}]}}]
}
```

Резултат: `status` (`OPTIMAL`, `FEASIBLE`, `INFEASIBLE`, `UNKNOWN`, `MODEL_INVALID`), `lessons` (по един запис за всяка
част и блок: `course_id`, `part_id`, `day`, `start_period`, `length`, `room_id`), `objective`, `solve_time_s` и
`conflicting_constraint_ids`.

Четенето е строго: неизвестни ключове се отхвърлят. `problems()` връща списък от `Problem(code, path, detail)`.
Кодовете са постоянни, за да може уеб частта да ги преведе: например `unknown_reference` (сочи към несъществуващ
запис), `bad_time_grid` (празнина в часовете), `no_matching_room` (няма подходяща стая), `conflicting_groups`,
`shared_teacher`, `bad_blocks`, `out_of_range`, `fixed_slot_block_count`, `bad_week`.

## 8.6. Решаващият алгоритъм

Код: [`solver/__init__.py`](../solver/__init__.py) и [`solver/diagnose.py`](../solver/diagnose.py).

**Модел.** По една булева променлива за всяка комбинация (учебен план, блок, ден, начален час), при която блокът се
побира в деня. Всеки блок има точно една избрана позиция. Заетостта на учебния план в даден слот е сума от тези
променливи, затова правилата за учител, групи и стая са прости неравенства „сума ≤ 1“ (или ≤ капацитета на стаята).
За частите, които изискват стая, има и променливи за избор на стая сред подходящите.

**Вградени правила:** учител, конфликтни групи (за всяка ученическа комбинация), капацитет на стая, блокове, части
едновременно, подходяща стая. При седмици A/B правилата се добавят веднъж за седмица A и веднъж за седмица B.

**Ограничения на училището.** Всеки вид има своя функция `_add_<вид>`. Всяко ограничение има свой „литерал за
включване“. Твърдите се добавят като задължителни. Предпочитанията добавят `тежест × размер на нарушението` към
една обща сума, която алгоритъмът минимизира.

**Бърза проверка за претоварване** (`solver/diagnose.py`). Преди същинското търсене се прави просто броене: дали
часовете на учител се побират в слотовете, които твърдите му ограничения оставят, и дали часовете на клас се
побират извън забранените му слотове. Ако не, резултатът е веднага `INFEASIBLE` с точно виновните ограничения.
CP-SAT би доказал това много по-бавно.

**Обяснение на невъзможността.** Ако търсенето завърши с `INFEASIBLE` и има твърди ограничения, моделът се изгражда
отново в „режим за обяснение“: литералите на твърдите ограничения стават допускания и CP-SAT връща набор от
допускания, които заедно са невъзможни (`sufficient_assumptions_for_infeasibility`). Това търсене е с една нишка и до
20 секунди. Наборът е достатъчен, но не винаги минимален. Празен набор означава, че причината е в самите данни
(без ограниченията на училището) или че времето не е стигнало.

**Минимални промени.** С `reference` (уроците на предишната версия) всеки блок, който напуска предишния си ден и
начален час, струва 1 точка (`MOVE_WEIGHT`). Това е просто още едно събираемо в сумата, затова твърдите правила
винаги имат предимство. Нови учебни планове, които ги няма в предишната версия, са свободни.

**Настройки на търсенето.** Лимит на времето `SOLVER_TIME_LIMIT_S` (60 s по подразбиране). Брой нишки = достъпните
процесорни ядра, но не повече от 8 (измерено: повече нишки от ядрата влошават резултата). Фиксирано начално число
на случайността (`random_seed = 0`). Винаги се пази най-доброто намерено решение.

**Измерени времена** (26.11.2026, в тестовата среда): демонстрационното училище (12 класа) около 1 s;
примерното училище (27 класа, 648 урока) около 3–5 s до оптимално решение.

## 8.7. Независимата проверка

Код: [`checker/core.py`](../checker/core.py). Функция: `check(solver_input, result) -> list[Violation]`.

- Получава същите обикновени данни като алгоритъма плюс готовите уроци.
- Проверява отново **всяко** вградено правило и **всяко** потвърдено ограничение със собствен код, написан по
  спецификацията в `schema/contract.py`.
- Връща списък от нарушения: правило, засегнати записи (учител, клас, стая, ден, час, учебен план, част, блок),
  ключ на съобщението, твърдо ли е и номер на ограничението.
- Пуска се автоматично след всяко изграждане и преди всяка ръчна промяна.
- Празен списък означава „проверено, всичко е наред“. Резултат без разписание дава едно нарушение `no_timetable`.

Всички допускания на проверката са описани в началото на `checker/core.py` (например как се броят прозорците при
разделени класове).

Ключовете на съобщенията се превеждат на български в [`app/solve_text.py`](../app/solve_text.py). Основните:

| Ключ | Текст на екрана |
|---|---|
| `teacher_double_booked` | Учител има два урока по едно и също време. |
| `groups_double_booked` | Група има два урока по едно и също време. |
| `room_over_capacity` | Стаята е заета над капацитета си. |
| `room_mismatch` / `room_no_computers` / `room_too_small` | Стаята не отговаря на изискванията / няма компютри / няма достатъчно места. |
| `parts_not_simultaneous` | Частите на един учебен план не са в един и същ час. |
| `teacher_unavailable_day` / `teacher_unavailable_slot` | Учител има урок в ден, в който не работи / в час, в който не е на разположение. |
| `too_many_lessons` / `too_many_same_subject` / `teacher_too_many_lessons` | Повече часове на ден от допустимото (клас / предмет / учител). |
| `gap_in_day` / `teacher_too_many_gaps` | Прозорец при класа / повече прозорци при учителя. |
| `day_starts_late` | Денят на класа не започва от първия час. |
| `block_not_at_fixed_slot` | Блокът не е във фиксирания си час. |
| `infeasible_core` | Ограничението участва в конфликт, който прави разписанието невъзможно. |

## 8.8. Изкуственият интелект

Код: [`app/llm.py`](../app/llm.py) и [`app/llm_resolve.py`](../app/llm_resolve.py).

**Принцип:** ИИ само чете текст и предлага ограничения. Той никога не нарежда часове и никога не записва
директно потвърдено правило.

**Стъпки при „Предложи ограничения“:**

1. Проверки преди извикването: ИИ е включен, текстът не е празен и е до 1000 знака, лимитите (5 в минута на
   администратор, 100 на ден) не са надхвърлени.
2. Програмата събира данните на училището: учители, класове, предмети, стаи, учебни планове, звънец.
3. **Подсказки без ИИ** (`llm_resolve.py`): обикновен код намира в текста кои учители, класове, предмети, часове
   (например „след 12:00“, „първите два часа“) и дни се споменават, като разпознава българските форми (Иванова =
   Иванов, „петъците“, „11 а“, латинско „a“). Когато едно споменаване съвпада с няколко записа, подсказката казва
   „НЕЯСНО“.
4. **Извикване на модела** (Anthropic Messages API): системен текст с правилата, инструмент `propose_constraints`,
   чиято входна схема се **генерира** от Pydantic моделите, данните на училището (кеширани между заявките) и заявката
   с подсказките. Моделът отговаря с извикване на инструмента: списък от ограничения (с откъса от текста, от който
   идва всяко) и списък „не разбрани“ с причина на български.
5. **Проверка на всяко предложение** със същата проверка като ръчния формуляр: Pydantic схемата и
   `SolverInput.problems()` срещу данните на училището.
6. **Проверка на препратките:** ако предложението сочи учител или клас, който не е назован ясно в текста, то се
   отхвърля. Така грешен номер от дълъг списък не може да мине незабелязано.
7. Повторенията се махат. Валидните се записват със `status = proposed`, `source = llm` и оригиналния текст.
   Невалидните се показват като „не разбрани“ с причина. Нищо невалидно не се записва.

**Защити:**

- Текстът на администратора се поставя между тагове, а знаците `<` и `>` в него се заменят, за да не може да
  „затвори“ таговете. Системният текст казва, че заявката е данни, а не инструкции.
- Лимити на заявките и на дължината; препоръчва се и месечен лимит на разходите на ключа.
- Време за изчакване 120 s, един повторен опит, до 16 000 токена отговор. Грешките на услугата се показват като
  кратко съобщение на български; подробностите са в лога.
- Тестовете използват **записани** отговори и никога не викат платеното API.

**Защо не обучаваме собствен модел:** няма набор от данни, училищата нямат видеокарти, малките отворени модели
са по-слаби на български, а всеки нов вид правило би изисквал ново обучение. Потвърдените и отхвърлените
предложения се пазят и могат да станат набор от данни по-късно.

## 8.9. Версии, ръчни промени и сравнение

- Всяко изграждане е нов ред в `solve_jobs`. Ръчното преместване и възстановяването създават **нов** ред с
  копие на уроците и `base_job_id` към изходната версия. Нищо не се презаписва.
- Как е направена една версия се извежда от съществуващите полета (`app/history.py`, `how_made`): има ли
  `started_at` и `base_job_id` и различават ли се уроците от изходната версия.
- Сравнението (`diff_lessons`) съпоставя блоковете вътре в една част и с една дължина: еднаквите се съкращават,
  останалите се класифицират като „сменена стая“, „преместен“, „добавен“ или „премахнат“.
- Публикувана е най-много една версия (`published_at`). Публикуването маха публикуването на всички останали в една
  транзакция.
- Ръчното преместване мести блока на всички части на учебния план, пуска проверката върху цялото редактирано
  разписание и иска потвърждение, ако има **нови** твърди нарушения.

## 8.10. Сигурност

| Мярка | Как е направена |
|---|---|
| CSRF | Flask-WTF проверява токен при всеки формуляр, който променя данни. |
| Роли на сървъра | Всеки адрес, който променя данни, има `@admin_required`. Тест обхожда **всички** адреси на приложението и пада, ако някой е пропуснат. |
| Ограничения на заявките | Вход и регистрация 5/мин; изграждане 5/мин; ИИ 5/мин на администратор и 100/ден; публична страница 60/мин на адрес; API 120/мин. Броячите са в Redis. |
| Пароли | Хеширани с Werkzeug. Няма пароли по подразбиране: `install.sh` пита за паролата на първия администратор, демо паролите идват от `.env`. Минимум 8 знака. |
| Вход | Съобщението не казва дали името или паролата е грешна. Проверката отнема еднакво време и за несъществуващ потребител. |
| Бисквитки | `HttpOnly`, `SameSite=Lax`, `Secure` (извън режим за разработка). |
| Обратен прокси | Заглавките `X-Forwarded-*` се приемат само ако `TRUSTED_PROXIES` > 0. |
| Импорт | Файлът е недоверен: клетките се четат само като текст (формулите не се изпълняват), всеки ред минава през същите формуляри като ръчното въвеждане, целият импорт е една транзакция. Ограничения на размера, на броя редове и на разархивирания размер (защита от „zip бомба“). |
| Грешки | Страници на български без технически подробности; API връща JSON. |
| Публични страници | Таен код от 16 случайни байта; само публикуваната версия; неизвестен и изключен код дават еднаква грешка 404. |
| API ключ | Сравнение с постоянно време (`hmac.compare_digest`). |
| Цвят на предмет | Проверява се формат `#rrggbb`, защото стойността отива в CSS. |
| Тайни и лични данни | Няма ключове, пароли и истински имена в хранилището. Примерното училище е анонимизирано (генерирани имена, преименувани стаи, разменени дни). |
